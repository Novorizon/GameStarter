# E 的U形场景：粗格心图遗漏连续通路

这是只读独立反例，不是候选E的一次成功运行，也没有重放原始出生历史。原正式E1b的失败保留：`u-obstacle` 56人全部生成，最终16攻击、39候场、1人仍Moving，到原tick12000截止。

最后移动者是id38，原r250、速度1000mm/50ms、原Goal588。实际位置为 `(31045.44858419952,14272.72429209976)`，原目标为 `(33500,15500)`，另55个身体固定在正式失败报告的真实位置。

## 两项独立证据

1. 对正式冻结DLL直接反射调用 `GlobalSearch.Find`：静态搜索有路，动态搜索返回null。`Connections`提供的8个静态合法格心都被驻留身体占据，动态连接数为0。这里没有重编译候选或修改其内部对象。
2. 独立几何查询找到原身体、原Goal不变的5段通路：从实际位置到 `(31000,14250)`、`(31000,14750)`、`(31250,15000)`、`(33000,15000)`、原Goal。长度3361.47mm，部分位置与其他身体恰好相切。用正式相同Core/Oracle DLL逐5ms实际走过：36微步、180ms；再稳定200逻辑tick。3,138,520次pair sweep、最小body gap 0mm、保持漂移0，最终16攻击、40候场。

Oracle从原正式失败状态中显式建立live请求字典，再验证零时长状态与后续实际运动。此操作仅用于从已有合法末态证明可行路径，不声称这些身体是在本见证中重新出生、移动到该末态，也不改变候选执行结果。

E的原动态A*仅使用1m原格心图；它不能表达部分格心间连续空隙。这是本项目离散化选择造成的漏路，不能据此认定物理无解，或推断Warcraft III商业引擎使用该图、具有同一缺陷。

## 复现与文件

```bash
python3 query.py
dotnet run --project Replay.csproj -c Release
```

需要Python3与.NET8 SDK。`FrozenDlls`保存与正式manifest逐字匹配的3个DLL；`frozen-source.zip`保存相应Core/Oracle/E候选源及编译生成源；`original-build-manifest.json`保留其原始构建绑定。输入原件、正式报告、查询、实际5ms见证状态与结果均收入目录。

`query.py`中的局部250mm查询范围只为生成这一个独立几何见证；它不是拟交付的通用算法，见证路线未提供给原候选。一般化修复应使用真实几何约束的精细连接或连续局部导航，再运行原矩阵；不能硬编码上述路径、放宽身体半径或更改原Goal集合。

`manifest.json`记录封存时所有证据的SHA-256。重新执行程序可能重写结果与日志，验原封存指纹时应先另复制目录。
