# C17死亡补队：实际循环与协同见证

这是只读审计，不是新的完整矩阵。原开发诊断在200个请求中，先39人实际到位，再死亡13人，最后累计生成48、活35、待生成152；活体中10攻击、23候场、2移动，tick8000失败。原报告的 `formalEvidenceReady=false`，本目录不把它改为正式结果。

该开发诊断的4份候选源与最终C17冻结manifest逐字相同。开发构建和最终冻结构建的DLL因构建路径规范化等差异而指纹不同；本审计使用最终冻结DLL，另实录重放原全部8014个API命令与80001个5ms步，最终状态逐字相同。原失败、原源指纹和最终构建manifest均保留，未修改C候选源码或公共框架。

## 已确证的事实

- **不能靠单体精细寻路走出去。** id46被id45、基地、id38、id48的膨胀圆组成的闭环包住。相邻圆严格相交，连接圆心的闭合多边形边界全部落入禁行圆并集；46在环内、原Goal57在环外。`barrier.py`生成解析证书。这只证明固定其他身体时不能独走，不能证明多体无解。
- **真实循环不是此前推测的40去57。** 只读字段记录显示，micro47810开始，46要求仍Moving的48临时去57；57恰是46的永久Goal。48到不了，micro49410、51010……79810每1600步超时后同帧重新得到57，实际位置保持 `(1984.3016377359143,4620.697285903864)`，Stuck涨到32600。40没有Yield57；micro37600后它的永久Goal56稳定。
- **临停点资格不足。** `RequestYield`只检查点上实际空闲与静态连通，不能据此得出从身体当前位置动态可达；协议还允许把请求者的最终Goal当作不可交换的临停点，同一失败可以无限重试。这是本项目目标与让路适配问题，不是《最高指挥官2》公开流场架构的商业原实现结论。

## 独立协同运动见证

保持所有身体r490、速度1000mm/50ms和最终Goal集合不变，只交换同profile、同target、没有显式AssignedGoal的40、45、46的Goal所有权：40→57，45→56，46→47。按顺序让48先垂直退到y4500再横退出生点、40横移、45上移、46进入腾出的位置，最后48回原Goal38。

共享正式Core/Oracle实际逐5ms验证：48微步、240ms，35人完成12攻击、23候场；再保持200逻辑tick。1,220,345次pair sweep，最小身体间距17.53mm，保持漂移0。先垂直再横退是几何需要，直接斜退会擦碰邻居。

此见证从已经检查过的失败末态建立Oracle live请求，证明存在协同恢复，不声称原候选执行了这些动作，也没有将见证路线或Goal分配提供给候选。剩余152个原始排队请求没有在见证中生成，**只恢复当前35人不能算原200请求场景通过**。

## 复现

```bash
python3 barrier.py
dotnet run --project Replay.csproj -c Release -- --inspect
dotnet run --project Replay.csproj -c Release
```

需要.NET8 SDK与Python3。`--inspect`仅重放记录的单场命令来暴露真实内部字段，并强制核对最终状态，未重跑整个矩阵；无参数运行是独立协同见证。`FrozenDlls`与最终manifest相符，`frozen-source.zip`提供对应源。`manifest.json`封存全部证据指纹；要重跑应先复制目录。

可评估的最小一般修复包括：拒绝动态无法执行的临停；不能合法交换时不占请求者Goal；在合法兼容、实际整段扫掠安全的情况下交换永久Goal并实际移动。仍需在原场景和其余输入中验证，不能因本见证存在便宣布修复成功，也不能硬编码这些ID、位置或顺序。
