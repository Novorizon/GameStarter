# 塔防寻路、避障与围攻

最终结果、运行命令和原始证据见[导航验收](Navigation/Verification.zh-CN.md)。

## 本次任务与证据边界

本次在 `feat/navigation-cooperative-recovery` 分支研究、实现和验收，对照实验保留各自分支。用户本次明确要求在分支上完成；不沿用此前交付约定自动合并 `main`。目标是让敌人沿合法区域移动，避开障碍与其他敌人，在目标周围取得实际可攻击的位置；先明确问题和方案，再用实验决定取舍。

本文引用的商业项目经验、论文和中间件说明用于证明方案来源与适用范围。它们不能证明本项目的实现正确，也不能代替真实地图、长期模拟和 Unity 表现验收。本次实现采用整数逻辑地图上的 **SIPP 安全区间搜索 + 按优先级进行完整路径预约 + 攻击位置与外圈集结协调**。这是本项目的组合与实现选择，不宣称商业游戏直接使用了同一套代码；若实验暴露根本限制，可以改变选择。

本次改造前的 `FightSession` 用累计距离在编辑折线上插值。敌人越过路线终点时立即扣基地生命并从列表移除，没有单位体积、同伴避障、持续攻击或目标周围站位。因此，“旧关卡能扣血”不能作为新围攻行为的通过证据。领域模拟固定每 tick 50 ms，坐标单位为毫米；这些规则继续与 Unity 场景、模型、动画分开。

## 需要解决的整体问题

### 1. 世界与单位的空间模型

- 地图哪里可以走，哪里是水、悬崖、装饰障碍、基地、建筑或边界？底图看起来像道路，不代表逻辑区域已经定义。
- 编辑路线是引导方向还是限制移动的走廊？本次允许沿可通行区域绕障，不能继续强迫所有敌人落在同一条零宽折线上。
- 单位的逻辑半径、建筑占地与视觉尺寸如何对应？不同体型的净空能否通过同一入口？模型替换不能悄悄改变碰撞规则。
- 是否允许斜向移动？必须同时处理静态拐角穿越、动态对穿和交叉边冲突。格心不在障碍内，不等于移动中的整个单位都安全。
- 基地外侧有多少可用的攻击位置、候场位置和绕行空间？这些位置是否在出生点的同一连通区域？
- 2D 底图、逻辑地图与 3D 表现使用同一份投影和坐标约定。镜头透视不能用来推断逻辑格大小。

### 2. 全局寻路

- 为每个敌人选择可达目标位置，而不是全部追基地中心。
- 绕过大障碍、U 形区域、断路和死胡同；局部排斥力不负责这些问题。
- 区分静态不可达、被未来预约暂时占用、搜索预算耗尽和候场容量不足。
- 处理多个出生点、不同速度、不同体型、连续波次和同时寻路请求。
- 路径缓存必须与地图版本、移动类型和目标匹配；地图或建筑变化后不能继续使用过期路径。

### 3. 同伴避让与移动执行

- 不能同一时刻占同一位置，也不能在两次 tick 之间对穿。
- 快单位追上慢单位、汇流、窄口、迎面相遇和交叉通行需要明确的等待或让行规则。
- 等待本身也占空间；不能只预约移动终点，却让等待者被穿过。
- 路径计划中的时间必须与实际移动耗时一致；转向、减速、暂停和状态切换不能使预约悄悄失效。
- 明确稳定的请求优先顺序，不依赖未规定的容器遍历顺序；新计划应经过统一校验后原子提交。优先规划允许不同提交顺序产生不同的合法结果，不承诺请求排列不变性。
- 逻辑位置只能有一个驱动者。表现层平滑、动画和物理组件不能反向把单位推到未经预约的位置。

### 4. 基地周围的攻击位置

- 攻击位置必须满足目标边界、单位体型、攻击距离、静态净空和进场路线。
- 槽位与实际位置是两件事：持有槽位不代表已经抵达，也不代表可以造成伤害。
- 槽位不足时安排合法候场；近侧有人不能成为远侧空位置永久空置的理由。
- 已攻击的单位不能堵死其他攻击位置的入口。候场位置也不能占住唯一入口或环绕通道。
- 稳定持有位置，避免每 tick 换目标形成抖动；死亡、离开和换目标时及时释放。
- 目标或障碍变化后重新校验；攻击过程中是否允许让行应有明确状态与恢复规则。
- 近战和远程不能仅通过同一距离阈值混用。后续增加远程时还需视线、射线遮挡、投射物规则。

### 5. 攻击与战斗状态

- 敌人的接近、候场、就位、攻击和重新就位必须可观察。
- 按实际逻辑位置检查攻击距离，按固定 tick 处理攻击间隔；不能因寻路返回“到达”而隔空扣血。
- 新持续攻击规则与旧终点漏怪规则不同；击杀、基地失败、波次结束、统计和结算需要一起核对。
- 无塔且基地高生命时，敌人应持续围攻或候场，不通过移除、传送、穿透或异常死亡清空问题。
- 暂停、选卡、失败、重新开局和离开场景时，预约、目标所有权与计时要保持一致。

### 6. 拥堵、死锁与恢复

- 合法等待：所有可达攻击位置均被实际攻击者占用，后续敌人在可用候场区等待。
- 调度阻塞：低优先级单位因为已提交路径或永久占位而无法前进，即使联合重排存在解。
- 真正非进展：有可达空位置或应当开放的通路，单位却长期没有进展。
- 几何无解：单位宽度超过通道净宽，或地图根本没有连通路径。
- 恢复应优先使用换可达目标、重新排序、局部协同重排和预定让行，保留诊断原因；不得用传送、忽略碰撞或从远处伤害基地掩盖失败。
- 反复重试需要上限、退避与事件唤醒，避免每 tick 重搜整张地图，也避免永远饥饿。

### 7. 性能、确定性与内容制作

- 少量到数百敌人的路径数量、预约区间数量、搜索展开数、最大计划时间和分配内存都需要度量。
- 整数坐标与固定 tick 有助于复现；稳定排序、冲突规则和预算处理也必须确定，不能只检查最终胜败。
- 手机性能需要实际设备验证；Linux 云端的领域耗时和 Unity 编译不能代表手机帧率。
- 建图工具应展示可通行区、净空、连通区域、目标/候场容量和当前预约，不能只输出漂亮底图。
- 先诊断算法和实现，再在必要时调整地图。采用逻辑格先行制图只能修正本关内容，不能被宣传为通用死锁算法。

## 实现方案：SIPP 安全区间与完整路径预约

### 选择依据

本项目暂为单人塔防，目标较稳定，逻辑已经使用整数坐标和固定 tick。让计划包含明确的移动时间、等待和占位，比在零宽折线上叠加排斥力更容易检查对穿、顺序依赖和长期阻塞。领域部分保持纯 C#，并通过真实 Unity 接入验收；当前未引入 ORCA SDK；这不表示 ORCA 不成熟，也不表示本方案在更多单位、更自由的移动中一定更好。

这里的“完整路径”指提交从当前状态到候选目标的可执行时间表，并保留到达后的占用，不是仅计划前几个 tick。当前默认规划范围为 4096 tick、单次计划最多展开 200000 个状态；范围相对于当前 tick 推进，不是整局时长上限。超出限制必须返回明确的预算状态；不能把截断结果称为到达，也不能声称有限预算下仍具有论文中的完备性。

SIPP 原文的状态为 `(配置, 安全区间)`，记录该区间内最早可达时间，并允许安全等待。它处理的是已知未来动态障碍轨迹下的单智能体路径。本文使用的群体方案在其外层逐个计划并预约，属于优先规划；不是原论文已经证明完备的多智能体联合求解器。[S2]

HCA* 中的层级启发式可以忽略时间与预约，为时空搜索提供下界；这个名称不要求一定将地图切成大区块。SIPP 与 HCA* 也不是同义词，不应因为都使用空间启发式而混称。[S1][S2]

### 必须维持的预约约束

| 对象 | 必须检查的内容 |
| --- | --- |
| 静态区域 | 单位整个占地及移动扫过区域合法，不仅检查格心 |
| 顶点占用 | 到达、离开、等待区间采用一致的开闭边界，接触 tick 不能重复占用 |
| 移动边 | 同向追赶、反向交换、交叉边和多 tick 经过中的冲突均被覆盖 |
| 单位体积 | 半径、相邻格间距与扫过碰撞模型一致；单格独占不自动保证大单位不重叠 |
| 时间 | 实际速度、移动持续 tick、等待与计划一致，不能执行未预约的插值捷径 |
| 目标 | 到达后持续占位；终点不能因路径完成而变成可穿过的空位置 |
| 当前存在的单位 | 尚未取得新路径也必须占有实际位置，不能在计划期间短暂隐身 |
| 新计划提交 | 原路径撤销与替换应原子化，失败保留安全状态；不能留下悬空预约 |
| 生命周期 | 死亡、离场、目标变化、失败和重新开局按所有者释放，不误删其他单位预约 |
| 表现 | 展示逻辑轨迹；不能由 NavMeshAgent、Rigidbody 或 Root Motion 另行改写逻辑位置 |

如果只允许四邻格移动，可先避免斜向边交叉这一类问题；仍需检查相邻单位实际半径与持续移动冲突。若后续加入斜向或平滑路线，必须扩展扫过碰撞和时间模型，再重新验收，不能只修改表现插值。

### 站位、进场与集结

攻击位置应围绕基地的实际边界生成，并先过滤净空、连通性、距离和进场条件。位置分配需要稳定的所有权、路径代价与候选排序，避免所有敌人追基地中心。优先保证攻击位置能够被利用，再为容量之外的敌人分配外圈集结位置。

集结不等于到达攻击位置，集结单位不能造成基地伤害。外圈必须有足够空间，且不能挡住剩余攻击位置的入口。地图上的“可达空槽”如果因为已停止单位而实际无法进入，不能仅凭静态连通判断为正常。

前排攻击者形成的人墙是动态障碍。仅给后排一个远侧空槽，再让它朝该槽前进，不保证有绕行路线。应检查占位后的进场连通性，保留通道，必要时对小范围单位安排换位或预定让行。攻击中的稳定持有是默认行为，不应成为不可撤销的永久封路承诺。

保护通路需要考虑整场会出现的体型与攻击距离，而非只检查当前新单位的目标集合。长射程单位的外沿攻击环可能包住短射程单位的内沿攻击环；内环对长射程单位既不是外沿攻击位，也不是候场区，只检查它自己的集合会漏掉封路。已知的所有波次定义应在开始分配前注册；运行中新增定义则需重新验证现有占位，不能仅创建一个新 profile 后继续宣称已有通路保证。

当前 API 契约为：开始生成前调用 `RegisterProfile(radius, attackRange)` 注册整场需要的组合；已有活跃单位后，未知组合会明确拒绝，不能静默创建。`FightSession` 在构造时注册敌人定义。分配时保护未占目标与出生入口的接入；已经占用的目标不强制永久保留一条空出口，否则会过早耗尽容量。死亡后的补位和重新进场由协同恢复实际执行，不能把“必要时可以让路”当作尚未执行的口头承诺。连通分量缓存不能漏掉同分量中的第二个出生入口。

`CountAttackSlots` / `CountGatherSlots` 只查询几何候选，不激活保护目录，也不改变骨架、路径和重放结果。目录是确定性输入的一部分，回放需要保持一致。独立调用 `TrySpawn` 在没有活跃单位时保留首次激活组合的方便路径，即使该请求随后未获准入；因此使用该路径的诊断回放还需记录失败请求，正式业务优先显式注册全部组合。

出生入口也必须在开始前通过 `NavigationGrid.SpawnCells` 完整声明；已有活跃单位后不接受未知入口。正式战斗配置在构造时核对每条路线入口，不能等到第二个出生点第一次刷怪才发现目录缺失。

## 独立方案审查：已知缺陷与补救方向

### 优先规划不完备

即使每次单体 SIPP 搜索都正确，先计划单位的选择仍可能使后续单位无路，而改变顺序存在可行解。下面的 T 字区域是最小反例之一，`A` 从侧袋去中央 `a`，`B` 从左侧去右侧 `b`：

```text
    A
    |
B - a - b
```

若先把 A 送到中央并永久占用，B 不能通过；若先让 B 通过，再让 A 就位，两者都能完成。重复搜索 B 或增大它的时间预算不能改变前面的永久承诺。[S3]

本项目需要监控可达空攻击位置和实际进展，对失败区分原因。补救可以是重新分配目标、在安全边界重新排序、让阻挡者退到已预约位置、对少量冲突单位进行协同重排。只添加随机抖动、只提高低优先级单位的搜索次数或只改变表现位置，不构成解决。任何补救仍需遵守碰撞约束，不允许传送。

### 目标永久占用与候场封路

目标占用到无穷是防止穿过静止单位的正确安全建模，但不能保证其他目标可达。尤其不能把桥口、唯一入口和环绕通道当作永久集结位置。攻击槽可以长期占用，前提是地图与分配支持其他需求；否则必须有可以计划的离位/换位协议。

把未规划单位的当前位置永久当障碍也是一种保守近似，可能误排除“它先走开就能通过”的解。应将其识别为调度限制，不把这种失败报告为静态地图断路。

### 体型、速度与执行偏差

单格预约的安全性依赖格间距与所有单位的有效占地。不同体型需要按占地扩展预约与静态净空，或明确采用足以覆盖最大单位的保守格；不能只增大显示模型。窄口可能对小单位连通、对大单位不连通。

即使只做四邻格移动，顶点与反向边检查也不自动保证圆盘安全。例如格间距为 `h`，A 同时从 `(0, 0)` 移至 `(h, 0)`，B 从 `(h, 0)` 移至 `(h, h)`；两者起终点不冲突，也没有交换边，但中点间距只有 `h / √2`。若两者半径之和大于此值，移动中就会相交。需要对移动段计算相对运动的最小间距，或采用足够保守的源/目标占用区间；仅规定 `半径 <= h / 2` 不充分。

基地圆形占地也要检查移动段。若基地中心不对齐格心，一条四邻格边的两个端点都可能在膨胀后的基地圆外，中段却进入圆内；例如边从 `(0, 0)` 到 `(500, 0)`，基地中心 `(250, 100)`，基地与单位半径之和为 `250`。不能只用端点 `CanOccupy` 证明整段安全。

不同速度意味着边占用时间不同。快单位追慢单位、等待后起步和多个 tick 的反向通行都要测试。如果实际执行中出现缓速、击退、眩晕或移动速度卡牌，新状态会使已有未来预约过期。应在加入这些玩法前定义安全重新计划方式。固定路径时间表不能被不受约束的局部推力或动画位移随意改写。

### 容量与进展不是同一件事

攻击位置满员时，后续单位合法等待；但必须能说明满的是所有可达位置，而非仅近侧位置。候场也有容量上限，有限地图不可能容纳无限敌人且全部互不重叠。出生点堵住时，应按明确规则排队生成，并保留应生成数量和等待原因，不能在出生点叠放或丢弃怪物。

按静态几何统计的攻击格数，不等于跨体型、跨射程、保留进场通道后的可同时驻留数量。例如外环可能有 28 个几何攻击格，但需要留 1 格供内环单位进场；不能把其余 27 个已使用和 1 个必要通道报告为“28 个实际攻击位全部可填”，也不能把所有未填格都解释成算法卡住。报告应分别给出几何候选、策略保留、可达空位与实际攻击数量，并用进场和补位实验核实保留通道的用途。

优先规划下的准入容量仍受已经提交的站位影响。即使接口返回当前策略的容量不足，也不能据此证明地图在任意联合重排下都无解。独立构造已证明可行的请求必须实际完成，不能将算法拒绝计为通过。只有独立容量上界能排除整批同时容纳时，才允许作为明确的超容量队列场景；排队者必须保留身份，并在死亡腾出空间后继续入场。

如果整个可通行区域都已饱和，应暴露容量状态；若实际关卡会达到该状态，需要调整波次、单位尺寸或地图空间。不能将等待数量静默截断后报告“全部正常聚集”。

### 搜索与预约的性能

安全区间减少的是逐 tick 展开的冗余，不会消除所有复杂度。大量轨迹经过同一窄口会产生多个不相交安全区间；逐个计划、扫描预约、尝试大量目标和长期持有历史路径仍可能昂贵。[S2]

完整路径计划较保守，长距离与长期等待会增加计划及预约维护成本。WHCA* 时间窗可以摊分计算，但会引入窗口外未知、频繁重规划、优先级公平与承诺终止方式，不能仅截短现有数组就宣称得到 WHCA*。[S1]

记录展开数、候选尝试数、失败分类、预约数量、最大寻路耗时和分配内存。在固定输入下反复执行，检查结果和预算状态能否复现。目标手机和 Unity 帧耗时另行测量，不能把论文硬件上的性能或云端结果作为设备预算。

## 端点与通行骨架排序

当贪心选择最近目标导致安全准入容量过早用尽，可以实验固定的停车端点与通行骨架。其研究依据是 well-formed infrastructure：长期停止的位置不应成为其他位置之间的必经点。Čáp 等人的连续圆盘定义要求任意两端点之间有路，对静态障碍保持最大半径 `r` 的净空，对其他端点保持 `2r` 净空；对应的 roadmap 也要保留这样的路径。[S11]

当前实现用通行骨架指导目标选择顺序，仍保留原有的预约、占地、目标可达和进出通道检查。这是排序启发式；它没有把所有通行骨架永久排除出目标集合，也不是 TP/COBRA 的理论完备实现。下面的固定通路证书用于明确区分更强的地图条件，不代替当前代码的实测。

Ma 等人的 MAPD 定义还要求任务有限、非任务端点不少于机器人数量、任意两端点可经不穿其他端点的路径连接。TP/TPTS 的保证依赖完整的任务分配、等待、腾出任务目标及路径更新规则，而非仅给地图添加几个停车位。[S12]

本项目可以独立验证如下空间条件，作为显式停车/通道测试地图的证书：

1. 定义永久通行集合 `C` 和停车端点集合 `P`，两者不相交；任何攻击或集结目标都不能永久占用 `C`。
2. 按最大单位半径检查 `C` 的静态净空和边的基地圆扫掠，确认它连通，所有声明的出生入口均能接入。
3. 每个可选停车端点都通过一条合法边接入 `C`。如此，两个端点可以经 `C` 相连，并绕开其余停车端点；这是本项目对该结构的空间论证，不是最优停车布局算法。
4. 对不同半径/攻击距离分别计算可用端点。端点总数足够，不代表每类单位都有足够的兼容端点；混合需求还要检查分配或匹配是否可行。
5. 独立证书检查与实际调度测试都通过，才报告该地图和数量通过；不能只验证骨架连通后跳过出生、移动、补位与攻击测试。

只把 `C` 外的目标排在前面、最后仍允许永久停在 `C` 内，是排序启发式，不具备上述固定通路条件。也不能用“端点良构”解释任意既有地图：更换 holding mask 属于内容/规则约束变化，必须与原场景结果分别记录，保留原有反例及真实业务地图至少 30 只无塔聚集的门槛。

当前共享出生点、外部待生成队列、异质目标集合、有限搜索预算与持续围攻规则不等同于论文中的任务系统。原证明还依赖机器人在独立端点开始、唯一未占目标、完整单体规划器和精确执行。固定通路可以支撑本项目进一步的活性分析，但不能让有限 horizon/searchLimit 或未实现的调度规则自动获得 TP/COBRA 的完备性保证。

更接近连续圆盘和异速的 TP-SIPPwRT 研究明确使用半径不超过半格、给定速度及可瞬时加减速的模型，并按方向、半径和速度计算时间余量；本项目“移动整段独占源和目标格”是更保守的自定义预约规则，不直接称为该论文的实现。[S13]

## 协同恢复与路径更新

静态目标排序能减少拥堵，但不能替代恢复。以下过程都由 `NavigationCrowd` 的独立模块负责，入口与表现层只使用业务 API。

1. **空位链搬移**：从真实空目标反向寻找一串可以挪动的单位。一次只让一个单位沿完整预约走入空位，旧目标成为新空位，直到空位接到入口或需要补位的攻击者。身体必须实际走完一段，才能继续下一段；不交换位置数组、不忽略已有单位。
2. **外侧让路与返场**：外环挡住更受约束的内侧单位时，先预约挡路者撤离，再预约内侧单位穿过，最后从未来的临停抵达时刻预约挡路者返回。完整事务成功才提交；失败恢复原路径和目标，当前 tick 与身体位置均不变。
3. **未来起点搜索**：返场搜索接受明确的 `planningStart`，从未来安全区间出发；它不能通过修改全局 `CurrentTick` 假装所有单位已经移动。出行与返场是同一个单位的连续时间表，中途状态仍为移动，不能在临停车位被算作完成聚集。
4. **死亡后的交通更新**：移除单位会释放对应的预约并更新交通修订。已经在格心、因旧预约等待的后续单位，尝试缩短到原目标的时间表；在边中途的单位先执行已预约的合法段。失败保留旧路径，不把身体直接推到新路线。
5. **搜索与稳定等待**：按修订缓存无变化的失败；目标或路径释放后失效并重新尝试。恢复同时记录展开数和搬移数。每一帧对所有候场单位重复洪泛不是合理的稳定等待策略。

原 4m 十字场景的 52/72 并不是物理容量：独立撤离/插入见证可以让原目标集的全部 72 人到位。该反例要求保留原地图、目标集合、体型、速度和出生分配，修复后全部实际入场；扩大地图或增加候选格的结果另列，不能替代它。

协同恢复仍有有限的规划预算，不宣称通用多智能体完备性。每出现一个可行而未完成的反例，就增加明确的自动化门槛并继续修复；不能只为拒绝换一个名称后结束任务。

## 验收设计

### 无塔长期围攻是独立验收项

使用真实业务配置的导航地图，禁止建塔，把基地生命设得足够高，并运行足够长时间。要覆盖实际路径最长的出生点、所有敌人速度/体型、密集生成和超过攻击位置容量的数量。长期测试不以敌人走到旧终点后消失为通过，也不以提前失败清空场景为通过。

| 条件 | 预期行为 |
| --- | --- |
| 敌人数低于可达攻击容量 | 每个敌人最终抵达合法攻击位置，开始符合间隔规则的攻击 |
| 敌人数等于容量 | 所有可达位置得到利用，无近侧堵住而远侧长期空置 |
| 敌人数超过容量 | 攻击者继续攻击，其余单位在合法位置等待；不能穿透或隔空攻击 |
| 删除一个攻击者 | 释放的位置与预约被正确回收，等待单位在限定时间内补位 |
| 多出生点汇流 | 不对穿、不叠放、遵守明确的稳定请求顺序；等候队伍最终有进展 |
| 长期满员等待 | 标记为容量等待；不发生每 tick 全量重搜、无限预约增长或无原因饥饿 |

持续攻击且基地不被打空时，战斗不会自然胜利，这是测试条件的正常结果。测试应观察围攻和调度，不通过修改胜败条件结束观察。

### 反例与压力矩阵

| 场景 | 主要检查 |
| --- | --- |
| 单位、空地图、直角与连续拐角 | 路径正确、距离与耗时一致、整个占地不越界 |
| U 形障碍与死胡同 | 全局绕路；不能靠局部排斥声称解决 |
| 断开的区域与过窄通道 | 可解释的静态不可达/净空失败，无无限重试 |
| 同格/交叉/反向请求 | 顶点与移动段冲突，包含 tick 边界 |
| 快慢混合、不同半径 | 追赶、预约持续时间与占地一致 |
| 先长射程外环、后短射程内环 | 跨 profile 的进场保护；内环空位置不能被外环永久封住 |
| T 字优先规划反例 | 显示不完备性；若有恢复，验证重新排序/让位而非传送 |
| 前排静止、远侧空槽 | 验证进场与动态阻挡；不能把拥挤到达当攻击 |
| 窄口双向与多路汇流 | 饥饿、死锁与恢复；单向生产关卡仍需算法反例测试 |
| 目标满员后死亡/离开 | 位置释放、补位与预约生命周期 |
| 高频连续生成 | 出生排队、应生成总数、容量边界 |
| 暂停恢复、不同 Step 批次、重开 | 时间一致、状态复现、无跨战斗预约残留 |
| 长时间与数百单位 | 预约增长、搜索预算、最大非进展时间与实际耗时 |
| Unity 真实场景 | 模型/底图与逻辑对齐、运动平滑、攻击表现不越过逻辑约束 |

### 必须报告的指标

- 计划/已生成/待生成/存活/死亡数量，不能漏算延迟出生。
- 已分配、已抵达和实际攻击人数；空闲可达攻击位置；候场与未分配数量。
- 静态侵入、单位重叠、移动段对穿、未经实际距离许可的攻击次数。
- 非进展时间与原因：计划等待、容量等待、不可达、搜索预算、调度阻塞。
- 因通道保护被否决的目标数量。只有有限时间预约消失才需要定时重试；静态断路、永久占位或通道保护不改变时，避免反复执行同一失败搜索。
- 攻击位置释放到补位的时间；换位次数；重复重规划与优先级饥饿。
- 区分重规划尝试、失败与成功次数；仅统计成功换位会漏掉等待者长期高频失败重搜。
- 单 tick 与完整测试的时间、展开数、预约数量和分配内存，以及运行平台。

一组测试通过，只能证明对应版本、配置、数量和平台的场景通过。未执行的地图、真实移动设备、速度变化机制或动态造塔不得写成已经验收。

## 什么时候才调整地图

先核对逻辑地图与底图，再定位算法和实现。如果验证发现出生点与基地不连通、通道净宽不足、攻击环完全没有绕行空间、候场区容量不足或永久位置切断唯一入口，应输出对应格子、净宽、容量和阻塞原因。

确认属于内容约束后，可以增加基地外侧可走区域、扩大入口、减少障碍或调整单位体型。必要时先设计通过模拟验收的逻辑地图，再依该地图重绘 2D 底图。地图修改必须保留反例测试，以免把缺陷移到下一个关卡；不能用放开所有草地、缩小单位到不可见或忽略碰撞取得假通过。
